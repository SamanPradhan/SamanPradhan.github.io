Letting people ask a 200-million-row database a question in English

NLP-to-SQL over attendance data, where a wrong answer is a wrong paycheck. Why accuracy had to be a number before it was a feature.

01 · Context

Truein records attendance for contract and multi-site workforces: every punch, shift, leave and correction, for every worker, at every site. That is 200M+ records spread over five tables that have to be joined to answer anything useful.

The questions customers actually ask are ordinary: who was late more than three times last month at the Andheri site; which contractors billed hours nobody scheduled. Each one used to become a report request and a wait. The brief was to let an admin type the question and get the number.

Two features came out of this: AI Analytics (ask a question) and AI TimeGuard.

02 · Problem

A language model will write SQL for anything you ask, with equal confidence whether the SQL is right or not. Over five joined tables the ways to be wrong multiply: a missed join condition doubles a count; a wrong date column shifts a whole month; a plausible column name that doesn't exist fails loudly, but one that exists and means something else fails silently.

The data is also multi-tenant. The model must never see, name or query another company's records, and it must never be the thing enforcing that.

And people are referred to by name. “Rajesh” might be four workers across two sites, spelled three ways in the source systems. A text-to-SQL answer about the wrong Rajesh is worse than no answer.

The failure mode that matters here isn't “no answer.” It's a confident wrong number that ends up on a payslip.

03 · Constraints

Real time: an answer had to come back while the admin was still looking at the screen, over the live 200M-row store, not a warehouse copy. Cost: every query is a model call plus a database scan, and both are billed. Tenancy isolation had to be structural, not prompt-based. And it had to run inside the existing NestJS backend and Aurora setup — no new data platform.

I set one more: accuracy would be measured on a fixed set of real questions before launch, and the number would be shown to the business, not asserted.

04 · What I built

A four-layer hallucination defense. The model's output is treated as a proposal, not a query. Each layer can reject it, and a rejection is returned as “I can't answer that reliably” rather than a guess.

L1

Schema grounding. The model sees a curated view of the schema — the tables, joins and column meanings that are allowed — not the raw database.

L2

Static validation. The generated SQL is parsed and checked against that view: only known tables, only permitted joins, read-only, tenant filter present.

L3

Guarded execution. Queries run under a scoped role with row limits and timeouts, so a bad query is slow and empty, never expensive or broad.

L4

Answer verification. The result is checked back against the question — shape, units, date range — before it's phrased for the user.

Identity-isolated mapping. The model never handles real identifiers. Tenant, site and staff identity are resolved outside the model and passed in as opaque handles; the tenant filter is injected by the system, not written by the model. Isolation holds even if the prompt is wrong.

Name resolution with Jaro–Winkler. “Rajesh at Andheri” is resolved to candidate records by an optimised similarity search before any SQL is written. One clear match proceeds; several matches become a clarifying question; none becomes an honest no.

The layers are cheap in the order they run. Most bad queries die at L2, before a single row is read.

05 · What happened

90%+ accuracy on the evaluation set, live over the full store, at a latency an admin will wait for. The refusal path turned out to be the feature people trusted: the system says no often enough that its yes means something.

Scheduled is what the brief asked for. Actual is what shipped.

06 · What I'd do differently

Build the evaluation set on day one, from real support tickets, before writing a prompt. I built it in week 12, and every week before that was guesswork dressed as progress.

Start narrower. The first version accepted any question; a version that accepted twenty question shapes and did them perfectly would have shipped sooner and taught me more about the twenty-first.
